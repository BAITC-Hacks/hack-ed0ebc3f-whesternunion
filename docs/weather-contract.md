# Архив погоды без утечки будущего

Файл `data/weather_forecasts.csv` используется веб-панелью. CLI принимает путь через `--archive`.
Это архив **прогнозов**, а не наблюдений. Формат UTF-8, запятая, десятичная точка:

```csv
turbine,issued_at,available_at,valid_time,wind_speed,temperature,source,kind
1,2026-01-31T06:00:00Z,2026-01-31T12:00:00Z,2026-01-31T19:00:00Z,7.4,2.1,provider/model/run-id,forecast
```

Строка выше — только пример формата, не реальная погода. Для запуска нужны все 24 или 48 часов.
Порядок и названия восьми столбцов сохранены. Новые поля добавляются в JSON-манифесты,
а не в этот CSV.

| Поле | Значение |
|---|---|
| `turbine` | 1 или 2 |
| `issued_at` | Инициализация конкретного прогона погодной модели, ISO 8601 с часовым поясом |
| `available_at` | Подтверждённое время доступности **всего экспортируемого 48-часового горизонта** в публичном архиве; одинаковое для всех строк выпуска |
| `valid_time` | Начало прогнозируемого часа, с часовым поясом |
| `wind_speed` | м/с, высота должна соответствовать датчику либо быть откалибрована |
| `temperature` | °C |
| `source` | Провайдер, модель, идентификатор запуска для аудита |
| `kind` | `forecast`; `observation`, `reanalysis`, `hindcast` не принимаются |

Алгоритм выбирает самый свежий **полный** запуск для турбины с `issued_at <= origin` и
`available_at <= origin`. Должно выполняться `available_at >= issued_at`. Поздние, неполные,
дублированные и нечисловые прогнозы не используются. Нельзя собрать один горизонт из новых
запусков, появившихся после начала расчёта. SHA-256 исходного архива сохраняется в отчёте.

Достоверность `available_at` и `kind` должна подтверждаться происхождением данных. Проверка
CSV не доказывает, что прогноз реально существовал в прошлом: нужны оригинальные файлы,
сведения провайдера и подтверждение публикации. Не присваивайте задним числом время
доступности реконструкциям.

## Точный час расчёта и границы

Для передачи между загрузчиком и replay зафиксирован ежедневный **origin = 23:00 UTC+5
(18:00 UTC)**. Это момент расчёта мощности, а не инициализация погодной модели.

| Параметр | Значение |
|---|---|
| Первый origin | `2026-01-31T23:00:00+05:00` = `2026-01-31T18:00:00Z` |
| Последний origin | `2026-02-28T23:00:00+05:00` = `2026-02-28T18:00:00Z` |
| Число ежедневных расчётов | 29, обе границы включены |
| Выпуск GFS (`issued_at`) | 12:00 UTC той же даты |
| Прогнозные шаги GFS | `f006` … `f053`, все 48 часов, без временной интерполяции |
| Первый valid_time | `2026-01-31T18:00:00Z` |
| Последний valid_time | `2026-03-02T17:00:00Z` = 2 марта, 22:00 UTC+5 |
| Итоговый объём | 29 × 2 × 48 = **2784 строки** |

Даты `--first-origin` / `--last-origin` включительны. Последний прогноз нельзя обрезать
концом февраля. Часовой пояс времени origin задан явно и не зависит от неподтверждённого
часового пояса исходных измерений. Тиммейт должен использовать эти же origin в replay.

## Источник: оперативный NOAA GFS

Используется публичный [NOAA GFS archive на AWS](https://registry.opendata.aws/noaa-gfs-bdp-pds/),
bucket `noaa-gfs-bdp-pds`, продукт `pgrb2.0p25`:

```text
https://noaa-gfs-bdp-pds.s3.amazonaws.com/gfs.YYYYMMDD/12/atmos/gfs.t12z.pgrb2.0p25.fFFF
```

Это исходные оперативные выпуски NCEP, не hindcast, наблюдения или реанализ. Загрузчик
проверяет не только имя файла, но и GRIB-метаданные: центр `kwbc`, статус `operational=0`,
тип данных `forecast=1`, время инициализации и валидности, параметр, высоту, единицы,
сетку 0.25° и мгновенный тип поля. Аналитические `f000` не используются.

### Доказательство времени доступности

Для каждого из 48 GRIB-файлов и его `.idx` сохраняются URL, HTTP-заголовки `Last-Modified`,
`ETag`, `Date`, идентификаторы запросов AWS и время текущего получения. Время получения
сейчас **не** выдаётся за историческую доступность.

`available_at` — максимум провайдерских `Last-Modified` всех используемых GRIB-объектов
и индексов в выпуске. Таким образом, на момент origin должны существовать все входы
48-часового прогноза. Если хоть один файл опубликован позже origin, отсутствует или
не имеет пригодного подтверждения, загрузчик завершится ошибкой, сохранив уже загруженные
оригиналы; успешный итоговый CSV не создаётся и предыдущий CSV не заменяется.

Основание: [документация системных метаданных S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html).
`Last-Modified` контролируется S3. Но для multipart upload это может быть **начало**
загрузки, поэтому загрузчик принимает только обычные 32-символьные hex ETag с отсутствующим
шифрованием либо SSE-S3 (`AES256`) и отклоняет multipart/неизвестные схемы. Нельзя просто
использовать `issued_at + 6h`, время в имени файла или дату поздней реконструкции.

Это подтверждение времени записи конкретных объектов **публичного оперативного архива**,
а не заявление о самом раннем распространении NOAA по всем каналам. Отдельных исторических
логов ACL или SNS-событий здесь нет. Поздняя перезапись объекта приведёт к отказу, а не к
присвоению ему более раннего времени. При диапазонных запросах `If-Match` и повторная проверка
ETag/Last-Modified привязывают полученные байты к проверенному объекту.

### Координаты, поля и преобразования

Используются координаты из задания, независимо от локальных переопределений live-режима:

| Турбина | Широта | Долгота |
|---|---:|---:|
| 1 | 43.645150 | 78.535604 |
| 2 | 43.643198 | 78.538828 |

- `UGRD`, `VGRD` на **100 м**, исходные единицы `m s**-1`.
- `TMP` на **2 м**, исходные единицы K; `temperature = TMP - 273.15` в °C.
- Билинейная интерполяция каждого компонента U/V по четырём соседним узлам; затем
  `wind_speed = hypot(U, V)` в м/с. Температура интерполируется отдельно.
- Все узлы, веса и исходные значения сохраняются в манифестах. Обе турбины находятся
  в одной ячейке; различия их прогнозов обусловлены только весами интерполяции.
- Часовая интерполяция не выполняется: все 48 шагов присутствуют в оперативных GRIB.

Высота датчика ВЭС неизвестна. GFS-ветер на 100 м **не откалиброван** к измерениям турбин.
GFS-поле является мгновенным прогнозом на valid_time, а целевая мощность — средняя за час;
это дополнительное ограничение модели, которое нужно учесть на этапе калибровки.
Восемь столбцов CSV не содержат единиц: одни только численные границы не могут обнаружить
правдоподобные значения, ошибочно записанные в км/ч. Единицы подтверждаются декодером и
происхождением исходных GRIB, а не угадываются по CSV.

## Воспроизводимый запуск

Загрузчик имеет отдельный модуль и не меняет CLI тиммейта:

```powershell
.venv\Scripts\python -m pip install -r requirements-weather.txt
.venv\Scripts\python -m wind_agent.weather_download fetch --workers 6
.venv\Scripts\python -m wind_agent.weather_download validate
.venv\Scripts\python -m wind_agent.weather_download validate --decode-raw
```

Общие зависимости проекта должны быть установлены заранее. Ключи OpenAI/AWS не нужны;
платные API не вызываются. Сеть требуется только для `fetch`, проверка `validate` офлайн.
Можно использовать от 1 до 12 HTTP workers. Временные сетевые ошибки, HTTP 429 и 5xx
повторяются не более четырёх попыток с задержками 1/2/4 секунды. HTTP 404, поздняя публикация
и ошибки содержимого не подменяются другим источником.

Для проверки одного выпуска, отдельно от окончательного CSV:

```powershell
python -m wind_agent.weather_download fetch --last-origin 2026-01-31T23:00:00+05:00 --output data/weather_smoke.csv
python -m wind_agent.weather_download validate --last-origin 2026-01-31T23:00:00+05:00 --output data/weather_smoke.csv
```

### Файлы результата и передача тиммейту

```text
data/weather_forecasts.csv
data/weather_forecasts.manifest.json
data/raw/gfs/YYYYMMDDT12Z/f006/manifest.json
data/raw/gfs/YYYYMMDDT12Z/f006/http-evidence.json
data/raw/gfs/YYYYMMDDT12Z/f006/source.idx
data/raw/gfs/YYYYMMDDT12Z/f006/temperature.grib2
data/raw/gfs/YYYYMMDDT12Z/f006/u.grib2
data/raw/gfs/YYYYMMDDT12Z/f006/v.grib2
... f007 … f053 для всех 29 дней
```

Сохраняются **неизменённые оригинальные GRIB-сообщения**, извлечённые HTTP Range из
глобальных файлов; это не полные глобальные контейнеры размером около 500 МБ каждый.
Манифесты содержат исходные URL и byte ranges, поэтому сохранённые сообщения можно
сопоставить с оригиналами. SHA-256 вычисляется для каждого сохранённого сообщения и
полного индекса, затем для их манифестов и итогового CSV. ETag не выдаётся за SHA-256.
Общий объём выбранных GRIB-полей — около 4 ГБ вместо сотен ГБ полных файлов.

Промежуточные результаты кешируются по выпуску/часу. Повторный `fetch` проверяет SHA-256
готовых исходников и продолжает незавершённые часы. Повреждённый кеш вызывает ошибку;
его нельзя молча использовать. Для отдельной чистой загрузки есть `--raw-dir`.
CSV заменяется только после полной проверки всех дней/турбин/горизонтов 24 и 48 часов.
`validate` дополнительно сверяет CSV с манифестом, все цепочки SHA-256 исходников,
провайдерские времена доступности и численные преобразования из сохранённых результатов
декодирования. `validate --decode-raw` дополнительно повторно декодирует все 4176 исходных
GRIB-сообщений и сверяет значения, единицы и статус оперативного прогноза независимо от
сохранённых результатов декодирования. Манифесты используют относительные пути, поэтому
каталог можно перенести.

`data/` уже исключена из Git общим `.gitignore`. **Обычный merge веток не передаст данные**:
передайте тиммейту этот каталог отдельно либо пусть он запустит загрузчик. CSV можно
использовать отдельно для replay, но для проверки происхождения нужен весь комплект.
Не добавляйте многогигабайтные GRIB в Git.

Полный интегрированный сценарий: `python -m wind_agent run-case`. Он автоматически
загружает этот комплект и отдельные 14 предтестовых выпусков для обучения, проверяет
происхождение, делает replay обеих турбин на 24/48 часов и сохраняет отчёт.
`python -m wind_agent run-case --offline` повторяет проверку без сети. Все 48 часов
последнего выпуска сохраняются; окно оценки отдельно ограничено февралем.

## Почему не Open-Meteo для этого исторического периода

Текущий Open-Meteo Forecast API подключён для live-режима. Он не используется для февраля.
[Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api) склеивает
начальные часы разных прогонов; эта временная серия не заменяет прогноз, доступный на
фиксированный момент расчёта.

[Single Runs API](https://open-meteo.com/en/docs/single-runs-api) позволяет выбирать
инициализацию через `run`. Однако документация указывает, что большинство моделей
архивируется с 2 апреля 2026, а более ранняя история ECMWF IFS HRES представлена
hindcast-реконструкциями. Поэтому этот источник **не подключён автоматически для февраля
2026**: нельзя выдавать реконструкцию за реально опубликованный тогда прогноз.
Время инициализации также не равно времени публикации.

Для этого периода вместо реконструкций используется описанный выше исходный оперативный
архив GFS. Наличие погодного CSV не означает завершённый бэктест модели: нужны
согласованный replay и фактическая мощность там, где рассчитываются метрики.
